# avarobe-api

Fastify backend for **Avarobe** (avarobe.com), an AI stylist: a person uploads a selfie plus height, weight, build and the clothing they shop for; we generate a full-body 2D avatar and a 12-season color analysis, then style complete outfits for an occasion and render them on the avatar. Looks are saved into collections per occasion. English, US-first.

Lives in the `Projects/Avarobe/code` workspace next to `avarobe-web` (it started inside the Trimry workspace and moved out on 2026-09-26). It shares conventions with `trimry-api` (Fastify 5, zod env, Mongo driver, JWT access cookie + rotating refresh cookie) but is its own service with its own database, cookies and domain. Product, research and operations docs live in `../../docs/`.

## Run

- `corepack pnpm --filter avarobe-api dev` (port 4100). Copy `.env.example` to `.env`.
- `corepack pnpm --filter avarobe-api test:auth` runs the password + passkey end-to-end check (software authenticator) against the running dev API and deletes its test account.
- Dev uses `MONGODB_DB=avarobe_dev` on the Trimry Atlas cluster and `STORAGE_DRIVER=local` (files in `.storage/`, served by `/api/v1/media/*` behind HMAC-signed, expiring URLs).
- In development, auth emails come back as `devLink` in the response unless the address is in `EMAIL_DEV_ALLOWLIST`.

## Flows

1. Auth (`modules/auth/routes.ts`, `passkeys.ts`, `utils/auth-links.ts`):
   - Password: `POST /auth/register {email, password, firstName?}` creates the account, signs in and sends a verification email; `POST /auth/login`; `POST /auth/password {currentPassword?, newPassword}` (signed in; revokes other sessions). argon2id, 8+ chars, per-account lockout after 10 failures for 15 min, uniform error with a timing-equal dummy check.
   - Email verification: one-time links (JWT + nonce hash on the user, 24 h). `POST /auth/verify-email/send` (signed in, 60 s cooldown), `POST /auth/verify-email {token}` confirms and signs in, returning `intent: 'passkey'` for passkey sign-ups.
   - Password recovery: `POST /auth/password/forgot {email}` always answers `{ok:true}` (60 s cooldown per account); `POST /auth/password/reset {token, newPassword}` (1 h link) checks the password before using the link, then sets it, verifies the email, revokes every session and removes passkeys.
   - Passkeys (SimpleWebAuthn v13) require a verified email to add: `POST /auth/passkeys/register/options|verify`, `GET /auth/passkeys`, `DELETE /auth/passkeys/:id`, usernameless `POST /auth/passkeys/login/options|verify`. Passkey sign-up is email-first: `POST /auth/register/passkey {email, firstName?}` sends the confirmation link; following it signs in and the web asks for the passkey. RP ID defaults to `APP_URL`'s hostname.
   - Email (`utils/email.ts`, MailerSend, tracking off): production sends everything; development only sends to `EMAIL_DEV_ALLOWLIST` and otherwise returns `devLink` in the response. Security notices go out when a password changes or a passkey is added.
2. `POST /avatar` (multipart: `selfie` required the first time, optional `bodyPhoto`, `heightCm`, `weightKg`, `build`, `presentation`, `consent=true` for new photos) normalizes photos with sharp (rotation, resize, metadata stripped) and starts a background job: the color analysis (Responses API, strict JSON; asked again once if a word in another script slips into its English, and a garbled photo note or swatch is dropped, `avatar/analysis.ts`) is saved the moment it's ready, and the render (Images API edits, `gpt-image-2`, streamed with 2 partial images) saves previews to `job.previewKey` as it goes. Client polls `GET /avatar` every 2 s and shows steps, palette and previews. Prompts insist on one coherent photograph (head-to-body scale, matching skin tone, 85mm framing); a full-body photo gives the real proportions.
   - `POST /avatar/refine {adjustments[], notes?}` edits the current avatar (current render + selfie + body photo as references) with targeted fixes (`more_like_me`, `head_smaller`, `head_larger`, `slimmer`, `fuller`, `broader_shoulders`, `narrower_shoulders`, `match_skin`). A failed refinement leaves the previous avatar ready.
   - Every render is kept as a version (6 most recent); `POST /avatar/versions/:id/select` switches back, `DELETE /avatar/versions/:id` removes one (deleting the version in use switches to the newest left; the last one can't go). `DELETE /avatar` removes the avatar, every version and both photos (looks stay). `DELETE /avatar/body-photo` removes the full-body photo. Creating or refining counts against `DAILY_AVATAR_LIMIT` (default 8).
3. `POST /looks {occasion, notes?, count 1-3}` plans the looks synchronously (stylist prompt + palette + body + taste profile) and renders each in the background from the avatar image plus the selfie as face reference, streaming a preview into `previewKey`. Client polls `GET /looks?batchId=`. When the batch spends someone's last credit (not comp), the stylist plans more looks up to three in the batch (at least one; a new account's single look comes with two), saved as `status: 'locked'` with its plan but no render and no credit; `POST /looks/:id/unlock` draws it for one credit (402 `no_credits` otherwise, which opens the offer with that look behind it; claimed atomically, so a double tap charges once) and fires `look_unlocked`. Locked looks refuse feedback and remix, and don't count in lifecycle emails or admin render stats. Retries and unlocks set `renderStartedAt` (serialized, `createdAt` before that) so the web's timer starts then.
   - The stylist (`looks/prompts.ts`, `AI_STYLIST_MODEL`=`gpt-5.5`, `AI_STYLIST_REASONING_EFFORT`=low) first writes the brief it understood (`asks`, shown back as "We heard", the decoded signature of any style, icon, era or music they named, and the weather), then designs looks that all stay on it: variety within the named style, never away from it; the style's signature colors translated to the person's palette; clothes that fit the weather. Each look lists the taste lines it used (`plan.tasteApplied`, only lines really in the profile). Formality comes from the event, not the venue's name (a date at a cocktail bar is date-night dressing, not cocktail attire), and dressy womenswear avoids the satin-wrap-dress template and mother-of-the-bride pieces (every rated cocktail-wedding and bar-date look got a thumbs down until 30-sep); a `fix` replaces each disliked piece with a different kind of piece. Measured with `evals/stylist/` (brief hits 59% → 84% against the old prompt on `gpt-5.4-mini`; dressy looks 11% → 89% and fixes 31% → 75% in `dressy-eval`; see its README).
   - Feedback and taste (`modules/taste/`): `POST /looks/:id/feedback {rating up|down, aspects[], pieces[{index, vote}], note?}` and `DELETE /looks/:id/feedback`; favorites count too. Each one schedules a background learning pass that turns the last 30 reactions (+10 favorites) into `tastes` (one doc per user): a summary, loves and avoids. Lines the person writes (`source: 'you'`) are never rewritten; learned lines keep their wording between passes, and removed ones go to `dismissed` so learning never brings them back. `GET /taste`, `PATCH /taste {statement}` (their own words, the strongest signal), `POST /taste/notes {list, text}`, `DELETE /taste/notes/:id`. A pass left running by a restart is resumed at boot (`resumeTasteLearning`).
   - Remix: `POST /looks/:id/remix {change, detail?}` plans one variant with the same style DNA (`colors`, `season` + optional season, `dressier`, `casual`, `occasion` + text, `surprise`, `custom` + text) or `fix`, which restyles a look from its thumbs-down feedback. One credit, rendered like any look; stores `remixOf` and `remix`. `GET /looks?remixOf=` lists a look's remixes.
   - Try-on: `POST /looks/try-on` (multipart `photo`, optional `notes`) reads the outfit in any photo (store listing, Pinterest, a model) into a look plan with the person's palette (`fromPhoto: false` marks pieces added to complete it), saves the photo as `referenceKey` and renders it on the avatar with avatar + selfie + photo as references. The prompt forbids taking the face, body or pose from the photo. Counts as one look.
   - Icon looks (`modules/looks/icons.ts`, `icon-routes.ts`): 20 try-on references (10 menswear, 10 womenswear) inspired by iconic style archetypes and eras, worn by the fictional demo people and named by the aesthetic ("Sixties Cool"), never after a real person: no celebrity names or likenesses anywhere (right of publicity). `GET /looks/icons` lists the ones for the avatar's `body.presentation` (unisex or no avatar: both, alternating) with the web's image path (`/icon-looks/<id>.webp`). `POST /looks/icons/:id/try-on {notes?}` is the upload try-on with the catalog image (`assets/icon-looks/<id>.jpg`, copied under the person's prefix as `referenceKey`): the stylist reads it for the person's palette, the plan keeps the catalog's name and pieces, and the look stores `iconId`. Images come from `../design/ai-samples/icons/generate.mts`, which reads the catalog.
   - Pieces: `POST /looks/:id/pieces` renders one product photo per garment (1024², white background, no person) from the look image (+ the try-on photo), 3 at a time, into `look.pieces[]`. The first breakdown of a look counts against `DAILY_PIECES_LIMIT` (6); calling it again retries only failed pieces, free.
   - Store search (`modules/shop/`): `GET /looks/:id/pieces/:pieceId/shop?market=cl&localOnly=true&offset=0` uploads the piece photo to SerpApi and runs Google Lens (`type=products`, then the same with the garment name as `q`, then `visual_matches`), localized by `country`/`hl`. Results are deduped, cached per piece and market in `shop_searches` (3 days), and a new paid search only runs when a page reaches past the cache. `localOnly` keeps stores of that country: its ccTLD (.cl, .com.mx, .co.uk) or a country path (zara.com/cl/, hm.com/es_cl/); for the US, anything that isn't another country's. Social and stock-photo sites are dropped. Each Lens call counts against `DAILY_SHOP_SEARCH_LIMIT` (60). Without `SERPAPI_API_KEY` it answers 503 and the web shows "coming soon". `GET /looks/markets` lists the markets.
   - Only piece photos (no people) ever go to the search provider; selfies, avatars and looks never do.
   - Billing (`modules/billing/`, price list of Sep 28 2026): the Color Report ($14.90) and Style Report ($9.90), one-time and kept for good (`colorReportAt`, `styleReportAt`); both for $19.90 (`reports_bundle`), or the other one at the bundle difference within `REPORT_CREDIT_WINDOW_DAYS` of buying one (`color_addon` $10, `style_addon` $5); the look pack (+10 looks, $9.90, never expire); and Avarobe Pro, a subscription: monthly $10.90 or annual $59.90, 30 looks a month (monthly plans get them with each invoice, annual ones at purchase and then from `refillAnnualCredits`, a scheduler that adds them a month apart until the paid year ends), try-ons, pieces and stores, the look analysis and unlimited avatar changes; Pro includes both reports while it lasts (monthly, annual and the trial); annual keeps them for good (`colorReportAt`/`styleReportAt`). Since 1-Oct-2026 the trial is off (`PRO_TRIAL`, default off; 'on' brings it back): `/billing/offer` returns `trial: null`, `trialEligible` is false and `pro_trial` checkouts are refused, so the web leads color offers with the Color Report ($14.90 once, preselected) and Pro monthly under it, and the offer emails lead with the report (the looks offer keeps Pro first, with the report as the one-time option). When on, the first-time offer is the Pro trial (`pro_trial`): `PRO_TRIAL_DAYS`=7 of Pro for `PRICE_PRO_TRIAL_CENTS`=$1 with `PRO_TRIAL_CREDITS`=10 looks, then Pro monthly. One per account (`billingState.trialEligible`: never had `pro` nor `proTrialAt`). Checkout is a `pro_monthly` subscription with `trial_period_days` plus the one-time trial fee price on its first invoice (Stripe's newer Trial Offers don't work with Checkout); the subscription metadata carries `trial: 'pro_trial'`, and that first invoice (`billing_reason: subscription_create`) is granted as the trial by the success page or `invoice.paid`, same key: `pro.status: 'trialing'`, `pro.trialEnd`, `proTrialAt`, +10 looks. The first monthly charge when the trial ends is a normal renewal (+30 looks, `active`). Canceling during the trial (`/billing/pro/cancel`) ends it at the trial end with no charge. In-app browsers (Instagram, Facebook): nobody finished a checkout inside them (no Apple Pay or saved cards), so the web offers "Pay in Safari/Chrome": `POST /auth/handoff {next, attribution}` (signed in) returns a one-time sign-in link (`utils/auth-links.ts` purpose `handoff`, `HANDOFF_LINK_TTL` 15m, `next` limited to /studio paths) that the web opens with `x-safari-https:` (iOS) or a Chrome intent (Android); `POST /auth/handoff/email` sends the same kind of link by email (purpose `sign_in`, `SIGN_IN_LINK_TTL` 3d); `POST /auth/link {token}` uses either once, signs in (an emailed link also confirms the email) and returns `next` plus the ad ids of the first browser, which the web keeps as `_fbc`/`_fbp` so the purchase still reaches Meta. Events: `handoff_link_created|used`, `handoff_email_sent`. Fixing a look rated down is free (`looks/fixes.ts`): the first `fix` remix of each look with a thumbs down costs no credit (claimed atomically with `looks.freeFixAt`, given back if planning fails; `freeFix` looks retry for free), up to `FREE_FIXES_IN_A_ROW`=3 in a row from the original look (`freeFixes` counts them down the chain); looks serialize `fixFree` for the "Restyle it with my feedback · free" button. `POST /billing/pro/start` ends a trial early (Stripe `trial_end: 'now'`): the first monthly charge today (a `subscription_update` invoice, granted like any Pro payment: +30 looks, `active`); the paywall offers it, with the look pack and annual, when a trial runs out of looks (upsell stage `trial_low`). Reports bought in the window count toward Pro annual's first payment (a one-time Stripe coupon `avarobe_report_credit_<cents>`). `POST /billing/pro/annual` switches monthly to annual right away (Stripe proration, `always_invoice`, the payment must succeed; during a trial it also ends the trial, since Stripe would otherwise keep it and bill $0; a $0 `subscription_update` invoice never grants); `/billing/pro/cancel|resume` (no Customer Portal: its settings are shared with Trimry). Checkout shows the renewal terms next to the pay button (auto-renewal laws). Prices come from `PRICE_*` env vars (defaults in `config/env.ts`; the web's `lib/pricing.ts` `PRICES` mirrors them for the home page). `/billing/checkout` checks who can buy what. `GET /billing/offer`, `POST /billing/checkout {product, returnPath}`, `POST /billing/confirm {sessionId}` (the success page grants access right away) and `POST /billing/webhook` (raw body, signature checked; backup). Granting is idempotent (unique `purchases.stripeSessionId`: the session id, or the invoice id for Pro payments; in a transaction). Webhook events: `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `invoice.paid`, `customer.subscription.updated|deleted`. Prices are found by lookup key and created on first use. The Stripe account is shared with Trimry: only `metadata.app=avarobe` is handled. Checkout is branded per session (`branding_settings`: "Avarobe", the "a" icon from the web's `public/brand/`, ivory and ink, Inter); Stripe still shows the account name in its terms line, the Link note and receipts.
   - Funnel and measurement: one daily look cap for every plan (`DAILY_LOOK_LIMIT`, 40); looks are the real limit and running out of them is what returns the 402 upsell. Checkout stores the browser's GA client id and `_fbp`/`_fbc` in the session metadata (ids up to 1024 characters are accepted and never fail the checkout; one over Stripe's 500-character metadata limit is dropped); on the first grant `billing/conversions.ts` reports the purchase to GA4 Measurement Protocol and Meta CAPI (deduped by session id; no email) when `GA_API_SECRET` / `META_CAPI_TOKEN` are set. Meta events go out with either `_fbp` or `_fbc` (plus IP and user agent): until 30-sep they needed `_fbp`, and the first trial (a buyer without that cookie) never reached Meta. `GET /billing/admin/funnel?days=` gives the database funnel (Pro members by interval, MRR with annual at a twelfth); admins can also switch their comp off (`/billing/admin/preview`), jump their own account to any plan stage (`/billing/admin/simulate`: free (the sign-up looks), free_used, pro_trial, color_report, style_report, reports, pack, pro_monthly, pro_low, pro_ending, pro_annual; Pro there is `sim_admin` and never reaches Stripe) or reset to a fresh free account (`/billing/admin/reset`).
   - Entitlements (`billing/entitlements.ts`): free = avatar (`FREE_AVATAR_RUNS`=2 renders), season + 3 colors (the serializer withholds the rest without the Color Report), `SIGNUP_CREDITS`=1 look stored on new accounts (accounts from before, without a stored number, keep `FREE_CREDITS`=3), their best and worst color on their face (below), the hair read and the ideal cut on them (`FREE_HAIR_RUNS`=1). Every recommended haircut comes with the Style Report or Pro (`hairCuts`, `needs_hair`); a haircut they describe or bring is a Pro try-on (one credit). Looks, remixes and try-ons spend one each (refunded when a render fails or is interrupted). Pro features answer 402 `needs_pro`, the reports `needs_color_report` / `needs_style_report`, and running out `no_credits`; the web opens the matching offer from the code. `COMP_EMAILS` get everything with no limits. `billingState` also gives the add-on and report-credit windows and `paid` (bought anything; `paidAt` on the user). The legacy `styleKitUntil` (first price list) still counts as Pro plus both reports until it ends. The user payload carries `billing`.
   - Reports (`modules/report/`): the Color Report unlocks `POST /report/color`, the drape test and the color boards; the Style Report unlocks `POST /report/style` and the style boards (`GET /report` returns each half only with its report, with `colorAvailable` / `styleAvailable`). `POST /report/color` writes the advanced color report (their coloring, scales, 26 colors, combinations, guides, 3 game changers, and the tests below) and starts the drape test (one 1024² image of the avatar in 2 flattering and 2 unflattering drapes); `POST /report/style` writes the style profile (archetype, where it shines, how to adapt it, fit guide, signature pieces, 12-piece capsule, silhouette and neckline tests); `POST /looks/:id/analysis` scores one look (dress code, palette) with tips. They're stored on the avatar or look; a new selfie clears the color report, drape and every board, a new body clears the style profile and the style boards.
   - Free drape preview (`avatar.drapePreview`): one 1536x1024 image of their face in their best color (`colorAnalysis.bestColors[0]`) next to their worst (`avoidColors[0]`), the proof before the offer. It starts when a new avatar is ready (`startDrapePreview`, once per selfie; a failure can start again after 5 min, a stuck one after 10), or from `POST /report/preview` for avatars made before it; `serializeAvatar` returns it to everyone (`drapePreview {status, url, best, worst}`). A new selfie clears it.
   - Report boards (`report/boards.ts`, `avatar.reportBoards`): one `gpt-image-2` image per test comparing options on the person, labeled by the web (panels in reading order, wear before avoid). Color boards come with the color report: neutrals, whites, face (lips, or shirts for menswear), hair (current + 3 colors; facial hair styles for menswear, `hairTest.kind: 'beard'`) as 2×2 portraits from avatar + selfie, metals as a wide pair, palette looks as 4 full-body outfits from the avatar. Style boards come with the style profile: silhouettes (full body, one neutral, shoes spelled out), necklines (portraits) and the capsule (a text-to-image flat-lay, no references). They render 3 at a time (~30 s each); a board's `updatedAt` marks its run, so an older run or a cleared report never takes its slot (the orphan image is removed). `POST /report/boards/:kind/retry` retries a failed one with its report's access (Color Report for color boards, Style Report for style ones). Reports never cost credits: one from before the boards (no tests) is simply written again with `refresh`, and gets boards then. Writing a report (color or style, including rewrites) counts against `DAILY_REPORT_LIMIT` (6), since each one renders its boards.
3b. Hair studio (`modules/hair/`, `/hair`): what haircut suits the person, shown on them, and the one they choose put on their avatar.
   - `POST /hair/profile` reads the selfie in the background (`AI_STYLIST_MODEL`, ~30 s) into `avatar.hairProfile`: face shape (+ why), hair type (texture, density, current length and cut), a summary, 3 principles that flatter, 2 to skip, and 6 recommended cuts (`r1`..`r6`, best first; each with length, why, maintenance, daily styling minutes, `stylistBrief` for the salon and `render`, the description for the image model, never sent to the web). Their natural hair color stays in every cut (color belongs to the color analysis), menswear gets men's cuts, the taste profile is respected, and no real person is ever named. Only the run that started can finish (`hairProfile.startedAt`); a selfie without a readable face and hair fails with advice. When it's ready, the ideal cut (`r1`) starts rendering right away if the person may have it.
   - Each haircut is a `hairstyles` document rendered as a chest-up 1024x1536 portrait from avatar + selfie (~30-50 s, streamed previews). `POST /hair/styles {recommendationId}` shows a recommended cut: free with the Style Report or Pro (`billingState.hairCuts`), otherwise the free hairstyle (`FREE_HAIR_RUNS`=1, `users.freeHairRuns`), else 402 `needs_hair`. A cut already shown isn't rendered or charged again; a failed one is retried in place. `POST /hair/styles/custom` (multipart `description` and/or `photo`) is "try any hairstyle": Pro and one look credit; the stylist reads the request (and the photo, taking only the haircut, never the person) into a name, render, stylist brief and an honest `fit` (great/good/tricky + note), then it renders with the photo as image 3. A failed render gives back the credit or the free hairstyle and the day's `hair` allowance (`DAILY_HAIR_LIMIT`, 20; the read counts too). `DELETE /hair/styles/:id`. A new read unlinks earlier recommended haircuts (they stay in "Cuts you tried").
   - `POST /hair/styles/:id/apply` puts a ready haircut on the avatar: an avatar job `kind: 'hair'` edits the current render with the portrait as image 2 (only the hair changes) into a new version with `hair {hairstyleId, name, render, refKey}` (`refKey`: the avatar's own copy of the portrait, so deleting the haircut doesn't break it). It counts as an avatar change (`useAvatarRun`: free runs, unlimited with Pro; 402 `needs_pro` otherwise). A failure leaves the avatar as it was. `POST /hair/natural` switches to the newest version without a studio haircut. `GET /hair` returns the read, the haircuts (with `onAvatar`), the current haircut and the avatar's state for the page.
   - The haircut follows the version in use (`avatar/hair.ts` `currentHair`): looks, try-ons, portrait report boards and the drape test add its close-up as the last image with a line saying that hair wins over the selfie's (`hairReference`); refinements and re-renders with new measurements keep it (the new version inherits `hair`); a new selfie brings its own hair back and clears the read and every haircut (like the color report). Versions can share a close-up (`orphanHairKeys` only removes one no remaining version uses). Deleting the avatar or the account removes haircuts and close-ups.
   - Server events: `hair_profile_started`, `hair_profile_ready`, `hairstyle_ready` (`source`, `free`), `hair_applied`, `hair_apply_failed`, and `avatar_started` with `kind: 'hair'`.
4. Collections: `GET/POST /collections` (POST with a name that already exists, in any capitalization, returns that collection instead of a duplicate), `GET/PATCH/DELETE /collections/:id` (`?withLooks=true` also deletes its looks, including from other collections), `POST /collections/:id/looks`, `DELETE /collections/:id/looks/:lookId`. `DELETE /looks/:id` removes a look and its files.
5. `DELETE /me` hard-deletes the account and every stored file (promised in the privacy notice).
6. Ad visits (`modules/events/`): the web reports visits from Meta ads to `POST /events/arrival {stage: arrived|loaded, click?, path, campaign?, content?, inApp, mobile}` (public, rate-limited, anonymous): its middleware when the request arrives, the page once it runs. Sign-ups add `registered` from the fbclid in the `_fbc` cookie. `click` is a SHA-256 of the fbclid (32 hex, `hashClick`), never the id; one document per click and stage in `arrivals` (TTL 180 days). `/billing/admin/funnel` returns `ads: {arrived, loaded, registered, inAppArrived}`; compared with Meta's link clicks it shows where clicks get lost.
   - Sign-ups are also reported to Meta from the server (`billing/conversions.ts` `reportRegistration`, CAPI `CompleteRegistration`, browser ids + IP + UA, never the email) with the same `eventId` the pixel used, when `META_CAPI_TOKEN` is set and the browser sent `_fbp` or `_fbc`: `/auth/register` and `/auth/register/passkey` accept `attribution {fbp, fbc, gaClientId}` and `eventId`.
7. First-party analytics (`modules/analytics/`): `POST /analytics/track` (public, 300/min, text/plain or JSON) stores web events in `analytics_events` (TTL 400 days) with the visitor, session, the signed-in user if any (access token, optional), the first touch (channel, campaign, content) and the session channel. Campaign tags are cleaned, never a reason to reject; an unreadable first touch is dropped. Sign-ups save `acquisition` on the user (channel, UTMs, landing, gclid/gbraid/wbraid/fbclid). Server events inherit it (`trackServerEvent`, never throws): `signup_completed`, `avatar_started`, `avatar_ready`/`avatar_failed`, `looks_styled`, `paywall_blocked` (every 402, with code and route, from `sendPaywall`), `checkout_created` (product, amount, placement from the checkout body) and `purchase_completed` (each payment). `GET /admin/analytics?days=&channel=` returns funnel, sources, offers, blocked, products, pages, daily, events, states and recent (`analytics/report.ts`; admins and their browsers excluded); `GET /admin/checkouts?days=` lists Avarobe's Stripe checkout sessions (paid, open, expired). `GET /admin/hair?days=` (`admin/hair-report.ts`) is the Hair studio's funnel (opened, read, got the read, saw a cut, put one on the avatar, saw a Hair offer, checkout from a `hair*` placement), cuts by kind, failures, clicks on the results cross-sell and the accounts that used it (short codes, face shape, cuts, on avatar, plan; no images).
   - Location (`analytics/geo.ts`): the web's middleware puts Vercel's reading of the visitor's IP in the `avarobe_geo` cookie (`US-TX`, or the country alone, `.avarobe.com`, 30 days). Sign-ups save it as `users.location {country, region, source: 'edge', at}` and web events as `geo`; server events copy the user's. We never look an IP up for this and keep only country and state. Accounts from before 29-sep were filled once from their first session's IP with an offline database (`source: 'ip'`; 14 of 35 got only the country). The report's `states` counts sign-ups (and avatar, looks, paid) by state and visitors by state from events.
8. Lifecycle emails (`modules/lifecycle/`): a scheduler in the API process (first pass 60 s after boot, then every 10 min) sends at most one onboarding email per account and pass. `schedule.ts` (pure, tested) picks the next one from the account's state: `welcome` (10 min to 3 d after signup; its copy follows how far they got), `avatar_nudge` (24 h to 7 d, still no avatar), `looks_nudge` (20 h to 10 d after the avatar, no looks yet; shows the season and the 3 free colors), and once the free looks are spent with nothing bought, the offer sequence, led by the Pro trial with the one-time options after it: `upgrade_offer` (3 h to 14 d after the last look), `upgrade_reminder` (2 days after the offer: the Color Report angle, with their free colors) and `upgrade_last_call` (5 days after the offer, "our last reminder"). Trial notices are transactional (sent even to people who turned off tips, no postal address, apart from the onboarding spacing): `trial_started` right after the grant (what was paid, when it renews, for how much, how to cancel) and `trial_ending` 48 h before the first charge unless canceled (`sendTrialNotices` in each run; simulated `sim_admin` trials are skipped). Any purchase ends the sequence. `checkout_rescue` (`sendCheckoutRescues`, every run): a `checkout_created` 1 to 48 hours old with no purchase since gets one email with a `sign_in` link back to that offer, in their own browser; promotional (opt-outs and the postal address apply), once per account, never to Pro members or admins. Each kind goes once, 18 h apart at least, and only to accounts from the last 30 days that aren't admins (`COMP_EMAILS`) or opted out. Sending claims the kind atomically on the user (`lifecycleEmails.<kind>`, `lifecycleEmailLastAt`) and undoes the claim if MailerSend fails. A legacy `kit_offer` counts as the offer.
   - Templates (`templates.ts`): table-based, inline styles, a preheader and a text part; images from `https://www.avarobe.com/email/` (`avarobe-web/public/email/`, made by `design/email/compose.py` from fictional-person assets). Links carry UTM tags (`utm_source=email&utm_medium=lifecycle&utm_campaign=<kind>`); `?upgrade=<reason>` opens the matching offer on the web. The offers say how Pro renews and show the prices from env.
   - Measurement (our own; MailerSend tracking stays off): every send is an `email_sends` document. Links back to the app are wrapped in a signed redirect (`GET /email/c/:id?u=&s=`, HMAC per link, only to the app's host), a 1x1 pixel (`GET /email/o/:id.gif`) counts opens (Apple Mail opens everything, so opens are a ceiling), and the unsubscribe link carries the send id so unsubscribes count per email. `GET /admin/emails?days=` gives, per kind, sent, opened, clicked, unsubscribed and purchases (last-click attribution: the last email clicked in the 7 days before buying) plus "bought within 7 days" of receiving one; the web shows it in `/studio/admin/emails`.
   - Opt out: every email's footer links to `/email/unsubscribe?t=<token>&e=<send id>` (HMAC of the user id with `JWT_ACCESS_SECRET`; works signed out) → `POST /email/unsubscribe {token, unsubscribe?, sendId?}` (rate-limited, also resubscribes), and the account page has the switch (`PATCH /me/email {tips}`; the user payload carries `emailTips`). Account and security emails are not affected.
   - The offers are promotional, so CAN-SPAM needs a postal address in them: they only go out when `EMAIL_POSTAL_ADDRESS` is set. `LIFECYCLE_EMAILS=off` stops the scheduler (on by default in production, off in development). `pnpm email:preview [email]` writes every email as HTML to `.email-previews/`; `scripts/lifecycle-e2e.ts` walks a throwaway account through every stage, the pixel, the click, the unsubscribe and the admin numbers against `avarobe_dev`, and cleans up.

## Guardrails

- `MONGODB_DB` must be `avarobe` or `avarobe_<suffix>`; the API refuses to boot against another app's database on the shared cluster (a copied Trimry `.env` once pointed it at `trimry`).
- Daily quotas per user (`DAILY_AVATAR_LIMIT`, `DAILY_LOOK_LIMIT`, `DAILY_PIECES_LIMIT`, `DAILY_SHOP_SEARCH_LIMIT`, `DAILY_REPORT_LIMIT`, `DAILY_HAIR_LIMIT`) via atomic counters in `usage_counters`; failed renders and failed searches give the quota back.
- Jobs are in-process. On boot, anything stuck in `processing` for 10+ minutes is marked failed (`utils/stale-jobs.ts`). Keep one PM2 instance.
- Measured (Sep 2026, `gpt-image-2` medium, 1024x1536): palette ~7 s, first avatar preview ~9 s, second ~19 s, avatar ready ~25-30 s; refinement ~25 s; look plan ~5-8 s, look preview ~7 s into the render, look ready ~25-30 s; try-on (analysis + render) ~35 s; 5 pieces ~65 s; hair read ~30 s, a haircut portrait ~30-50 s, a haircut put on the avatar ~25 s.

## Production checklist

- DNS: `avarobe.com` → web (Vercel), `api.avarobe.com` → EC2 (nginx → 4100).
- `.env`: `NODE_ENV=production`, `MONGODB_DB=avarobe`, `APP_URL=https://avarobe.com`, `API_PUBLIC_URL=https://api.avarobe.com`, `CORS_ORIGINS=https://avarobe.com,https://www.avarobe.com`, `COOKIE_DOMAIN=.avarobe.com`, new `JWT_ACCESS_SECRET`.

- Email: `avarobe.com` is verified in MailerSend (DKIM + SPF); set `MAILERSEND_API_KEY` and `MAILERSEND_FROM_EMAIL=hello@avarobe.com`. Set `EMAIL_POSTAL_ADDRESS` for the Kit offer email. `avarobe.com` has no MX yet, so mail to hello@ or privacy@ bounces: set up receiving before relying on those addresses (the terms name hello@ for refunds).
